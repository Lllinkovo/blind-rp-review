# Blind RP Review · RP 盲审

**把一份博士研究计划，变成有证据、有反驳、有修改顺序的审查报告。**

面向正在写博士研究计划（RP）的申请者、研究者，以及希望组织结构化审查的 Agent 用户。四个专项角色分别检查**研究问题、文献贡献、主张与来源、方法与推论**；一个裁决角色在报告冻结后处理分歧，给出最重要的修改任务。

[English](README_EN.md) · [完整运行示例](docs/DEMO.md) · [快速开始](#快速开始) · [项目与面试介绍](docs/PROJECT_COPY.md)

## 先看你会得到什么

| 你提供 | 审查过程 | 你得到 |
|---|---|---|
| 一份确定版本的研究计划或概念稿 | S0 记录范围与版本 → S1–S4 分项审查 → 校验并冻结报告 → S5 裁决 | 总体结论、具体证据位置、最强反驳、问题解决条件、最多三项优先修改 |

输入以正文为依据；已有人工评语另行保管，审查结论冻结后再比较。审查过程保持原稿不变。

**[查看实际运行记录与完整报告 →](docs/DEMO.md)**  
示例使用仓库中的虚构概念稿，保留各角色输出和校验记录。它展示这个工作流实际会产出什么；单个示例不能衡量一般学术审查准确率。

## 为什么做它

和 AI 多轮修改研究计划后，对话里会积累作者的解释、已经接受的判断和先前的修改理由。最终稿的读者却只能看到正文。这个项目针对的就是两者之间的落差：**对话里解释得通的事，正文是否真的给出了依据？**

因此，专项角色从新的上下文读取指定稿件，重新判断问题是否成立、贡献是否有支撑、方法能否回答问题。

## 核心设计与优势

| 设计 | 解决的问题 | 报告中的可检查结果 |
|---|---|---|
| 新上下文与限定输入 | 先前评语可能影响本轮判断 | 记录各角色拿到的材料与隔离方式 |
| 四类专项审查 | 一个笼统评价难以定位推理问题 | 分别定位问题、贡献、来源和方法上的发现 |
| 最强反驳检验 | 看似严重的问题可能已有合理替代方案 | 每个重大问题说明反驳、剩余缺口和严重程度 |
| 冻结报告与文件校验 | 审查途中换稿会混淆结论依据 | 用 SHA-256 和字节数对应明确版本 |
| 证据裁决与修改标准 | 分歧不能靠投票消除，建议也需要验收条件 | 保留关键争议，给出最多三项修复及清除条件 |

这些是已经实现的流程约束；是否优于普通审查，需要另外做匹配条件的对照评测。

## 快速开始

### 1. 准备运行环境

- 能读取本地文件、运行 Python 的 Agent；本仓库在 Codex desktop 中演示。
- Python 3.10+ 用于校验脚本，脚本本身只使用标准库。
- 完整模式需要能创建**不继承父对话的新子角色上下文**的宿主。没有这项能力时，报告会明确标记降低隔离的单上下文模式。
- PDF / Word 的文字提取由宿主提供；第一次试用建议用仓库里的 Markdown 示例。

仓库包含 skill 指令、审查模块和校验脚本。模型调用、角色调度、文档解析和相应费用由运行它的宿主承担。

### 2. 安装到 Codex

**Windows PowerShell：**

```powershell
git clone https://github.com/Lllinkovo/blind-rp-review.git "$HOME/.agents/skills/stress-test-phd-rp"
```

**macOS / Linux：**

```bash
git clone https://github.com/Lllinkovo/blind-rp-review.git "$HOME/.agents/skills/stress-test-phd-rp"
```

以上使用 Codex 当前文档中的用户级 skill 目录。打开新会话，确认可选中 `$stress-test-phd-rp`；若未发现，重启 Codex。已有同名目录时先比较版本，避免覆盖现有定制。目录发现规则见 [OpenAI 官方文档](https://learn.chatgpt.com/docs/build-skills)。

其他 Agent 宿主需要按自己的 skill 发现与子角色接口配置；本次示例只验证了记录中的 Codex 环境。

### 3. 发起审查

将 `proposal.md` 换成你的研究计划路径：

```text
用 $stress-test-phd-rp 盲审 proposal.md，使用中文输出。
保持原稿不变。各专项角色使用不继承当前对话的新上下文，
只读取指定输入；先检查宿主是否支持，并记录真实隔离方式。
先冻结审查结论，再给出证据位置、最强反驳和最多三项优先修改。
把本轮报告和校验记录放到单独的运行目录。
```

**复现公开示例：** 将输入指向安装目录内的 `examples/case-01/proposal.md`。新运行开始前，不要把已公开的示例报告或 `evals/expected.json` 交给审查角色；看过答案的上下文应换成新上下文。

## 工作流程与输出

```text
proposal.md → S0 范围与版本记录
                 ├─ S1 研究对象、问题、学科位置
                 ├─ S2 文献、缺口、贡献
                 ├─ S3 主张与来源
                 └─ S4 方法、推论、进入现场的条件
                          ↓ 四份报告冻结、输入重新校验
                      S5 证据裁决
                          ↓
              结论 + 具体发现 + 修改顺序
                          ↓ 可选
                    与人工意见比较
```

| 结论 | 含义 |
|---|---|
| `BLOCK` | 已证明的核心失败在最强反驳后仍然成立 |
| `MAJOR REVISION` | 存在重要问题，但有保留核心研究的修复路径 |
| `PASS FOR HUMAN REVIEW` | 本轮范围内未留下重大或重要缺陷，可交人工继续判断 |

运行目录通常包括 `S0_MANIFEST.md`、`S1_REPORT.md` 至 `S5_REPORT.md`、输入与报告校验记录，以及独立的调度日志。每项重要发现包含位置、证据、影响、最强反驳、置信度和解决条件。[完整输出规范](references/output-schema.md)

## “盲审”具体指什么

隐藏的是先前评价、预期答案和父对话；作者身份不会自动匿名化。新上下文不等于不同模型，也不保证偏差彼此独立。输入清单若仅靠指令约束，会如实标记为 instruction-based；文件哈希只证明内容一致。

无法创建新上下文时，从开始即标记 `REDUCED_ISOLATION_SINGLE_CONTEXT`。若声称独立的运行发生隔离失败，则标记 `RUN_INVALID_ISOLATION_FAILURE` 并重跑受影响部分。

维护者 [Lllinkovo](https://github.com/Lllinkovo) 将实际申请材料审查中的需求整理为可复用流程：定义 S0–S5 分工、限定角色输入、冻结阶段报告、用 Python 校验版本、维护虚构案例和测试。
